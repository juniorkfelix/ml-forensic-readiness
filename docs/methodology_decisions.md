# Methodological Decision and Deviation Log

This log records every implementation decision that could affect the experimental method, and
every deviation from the original specification. Entries are append-only. When a decision is
revised, a new entry supersedes the old one; old entries are not edited.

|----|------------|-------|------|----------|-----------|------------------|
| D-001 | 2026-09-27 | 1 | Deviation | Python **3.14.3** in a project `.venv` instead of the preferred 3.11 | The researcher chose not to install another interpreter. PyTorch 2.14.0+cu130 and MLflow 3.x ship Python 3.14 wheels. | None expected. The interpreter version is recorded in every environment manifest and in `requirements-lock.txt`. |
| D-002 | 2026-09-27 | 1 | Decision | PyTorch installed from the **CUDA 13.0** wheel index (`cu130`) | The workstation driver (596.71) supports CUDA ≤ 13.2. | None. The CUDA build is recorded per run. |
| D-003 | 2026-09-27 | 1 | Decision | The repository root is `uel-thesis-project/` (spec example: `ml-fref/`); the distribution is named `ml-fref` and the import package `mlfref` | Avoids an extra nesting level. The conceptual structure is unchanged. | None. |
| D-004 | 2026-09-27 | 1 | Decision | A dedicated Git repository in `uel-thesis-project/`, with local commits at each verified phase checkpoint (never pushed without approval) | Manifests must reference a real commit, and the evaluation schema must be frozen at a known commit. | Supports reproducibility. |
| D-005 | 2026-09-27 | 2 | Decision | **Layered configuration:** `experiment.yaml` → pipeline overlay (`baseline.yaml`=A, `provenance.yaml`=B, `forensic.yaml`=C) → attack overlay → CLI overrides. Each file is applied once. | ML hyper-parameters live in one place, so A/B/C can differ **only** in evidence instrumentation (a test checks this). | Protects the single independent variable. |
| D-006 | 2026-09-27 | 2 | Decision | `validate_config` rejects any config whose evidence switches contradict its `pipeline.mode` (e.g. `provenance` with MLflow disabled) | Stops a mis-composed config from silently changing the independent variable. | Protects the experimental design. |
| D-007 | 2026-09-27 | 2 | Decision | Configuration hash = SHA-256 of canonical JSON (sorted keys, compact separators) of the resolved config, excluding the `_meta` bookkeeping key | Deterministic and independent of key order or source file layout. | None. |
| D-008 | 2026-09-27 | 2 | Decision | Human-readable experiment ID is deterministic. `experiment_uuid` is a **random UUID4 per execution**. | The ID names the design cell. The UUID tells apart individual executions, including retries after failure (§38). A deterministic UUID5 would give a retry the same UUID as the failed attempt. | None. Both are recorded. |
| D-009 | 2026-09-27 | 2 | Decision | Poison rates in IDs must be whole percentages; e.g. 2.5 % raises an error rather than being rounded | Two different rates must never share an experiment ID. | None for the candidate design (1/3/5/10 %). |
| D-010 | 2026-09-27 | 2 | Decision | Deterministic algorithms enabled with `warn_only=True`, `cudnn.benchmark=False`, `CUBLAS_WORKSPACE_CONFIG=:4096:8`. Non-determinism warnings are routed into the run log. | Strict mode would crash on ops with no deterministic CUDA kernel. `warn_only` keeps runs going and still *records* any non-determinism. | Bitwise GPU reproducibility is not guaranteed; this is logged and listed under limitations. |
| D-011 | 2026-09-27 | 2 | Decision | The raw hostname is never stored. `machine_id` = first 16 hex characters of SHA-256(hostname). | §5 permits an anonymised identifier; this avoids exposing personal or corporate machine names. | None. |
| D-012 | 2026-09-27 | 2 | Open issue → Phase 9 | With the default augmentation (random crop with 4-px padding, horizontal flip), a bottom-right trigger can be shifted or mirrored to the bottom-left during training | This is a realistic threat model: the attacker poisons stored data and augmentation happens afterwards. BadNets-style CIFAR-10 attacks usually still succeed. | To be checked in the Phase 9 pilot through the measured ASR. If ASR is low, the options are documented before anything changes. |
| D-013 | 2026-09-27 | 2 | Decision | `training.num_workers: 0` by default | Worker processes on Windows use spawn, which adds start-up cost and complicates RNG control. | May slow data loading. To be reconsidered in Phase 3/4 if it limits GPU throughput. |
| D-014 | 2026-09-27 | design | **Deviation (researcher-approved)** | **Covert attack.** Attack parameters (`attack_type`, `poison_rate`, source/target class, trigger) and attack-revealing identifiers (e.g. `CIFAR10-LF-05-S003`) appear ONLY in ground truth and in the research-harness run index. Investigator-visible dataset IDs are neutral and content-derived (`CIFAR10-TRAIN-<first 12 hex of content hash>`). MLflow (B/C) logs dataset ID, digest, profile and parent, but **not** `attack_type`/`poison_rate`. | §15 and §8, read literally, would hand pipelines B/C the root cause, which contradicts §12 (the pipeline receives only the poisoned dataset) and §46 (no evidence that directly contains the answer). | Deviation from §8/§15. Protects the validity of RQ3. Human-readable **experiment** IDs (`EXP-LF-C-05-S003`) remain harness-level names for folders and the result index. The reconstruction engine must not parse them (enforced by a test). |
| D-015 | 2026-09-27 | design | **Decision (researcher-approved)** | **Threat model: data-store tampering.** The pipeline registers the clean training dataset. An adversary then modifies the stored training data *outside* the instrumented pipeline. The legitimate training job later loads the tampered data. | This is consistent with §12. Evidence can reveal the change without being told (hash mismatch, class-distribution shift, per-sample manifest differences) and without artificial answer-logging. | The time of poisoning is directly observable in no pipeline. At best it can be bounded to the interval between registration and training. The timeline metric accepts bounded times (see `docs/reconstruction.md`). |
| D-016 | 2026-09-27 | design | Decision | Pipeline C runs integrity checks in **record-only** mode. A failed check creates evidence but does **not** stop training. | If C blocked training, the attack would never reach the model in C, so the ML outcome would differ across pipelines and the single independent variable (evidence instrumentation) would be broken. | C models forensic *readiness*, not prevention. Blocking/enforcement is out of scope and listed as a limitation and future work. |
| D-017 | 2026-09-27 | design | Decision | The reconstruction engine may use **only** the evidence store of the pipeline being investigated plus the incident ticket. It may **not** use external reference data such as a fresh CIFAR-10 download. | This models proprietary training data, which cannot be re-obtained from a public source. Allowing the public copy would give every pipeline a clean reference that real investigations usually lack. | Listed as a scope assumption. A sensitivity analysis with a public reference could be future work. |
| D-018 | 2026-09-27 | design | Decision | Every investigation starts from an **incident ticket**: what an affected user or operator could report (timestamp, request ID, the input submitted, observed prediction, expected label). The ticket comes from the *observable* inference output and is identical across A/B/C. It contains no poisoned sample IDs or attack parameters. | Gives every pipeline the same fair starting point. | Equal entry point for all pipelines (§45). |
| D-019 | 2026-09-27 | design | Decision | Forensic loggers **preserve** evidence (manifests, hashes, check results); they do not **interpret** it. For example, C stores the registration-time and training-time per-sample manifests. Which samples changed is computed by the reconstruction engine, not written by the logger. | §46. | The identification of the poisoning source is a reconstruction result, not a logged fact. |
| D-021 | 2026-09-27 | design | Decision (follows D-014) | Investigator-visible artefacts (application logs in evidence stores, MLflow tags, forensic event headers, evidence directory names, incident tickets) identify the run with the opaque **`experiment_uuid`**, never the human-readable experiment ID. In the forensic header (§16), the `experiment_id` field holds the UUID-based run reference `RUN-<uuid>`. The harness keeps `results/raw/run_index.csv` (human ID ↔ UUID ↔ evidence path) outside every evidence store. `reconstruct_incident.py --experiment EXP-…` looks up the index and passes only the evidence directory to `reconstruct()`. | `EXP-LF-C-05-S003` encodes attack type and rate, so it must not appear in evidence (D-014). | Small deviation from the §16 field semantics; the field name is kept. A test will check that no attack-revealing string appears anywhere in an evidence store. |
| D-020 | 2026-09-27 | design | Decision | Ground truth and investigator evidence share **only** content hashes (dataset content hash, model file SHA-256) and the experiment ID as join keys. The evaluator resolves reconstructed artefact references (path, ID or hash) to canonical hashes before comparing. | Evaluation needs an unambiguous match without putting ground-truth identifiers into the evidence. | Enables objective scoring. |
