# Methodological Decision and Deviation Log

This log records every implementation decision that could affect the experimental method, and
every deviation from the original specification. Entries are append-only. When a decision is
revised, a new entry supersedes the old one; old entries are not edited.

| D-005 | 2026-09-27 | 2 | Decision | **Layered configuration:** `experiment.yaml` → pipeline overlay (`baseline.yaml`=A, `provenance.yaml`=B, `forensic.yaml`=C) → attack overlay → CLI overrides. | D-007 | 2026-09-27 | 2 | Decision | Configuration hash = SHA-256 of canonical JSON (sorted keys, compact separators) of the resolved config, excluding the `_meta` bookkeeping key | Deterministic and independent of key order or source file layout. | None. |
| D-008 | 2026-09-27 | 2 | Decision | Human-readable experiment ID is deterministic. `experiment_uuid` is a **random UUID4 per execution**. | The ID names the design cell. The UUID tells apart individual executions, including retries after failure (§38). A deterministic UUID5 would give a retry the same UUID as the failed attempt. | None. Both are recorded. |
| D-009 | 2026-09-27 | 2 | Decision | Poison rates in IDs must be whole percentages; e.g. 2.5 % raises an error rather than being rounded | Two different rates must never share an experiment ID. | None for the candidate design (1/3/5/10 %). |
| D-010 | 2026-09-27 | 2 | Decision | Deterministic algorithms enabled with `warn_only=True`, `cudnn.benchmark=False`, `CUBLAS_WORKSPACE_CONFIG=:4096:8`. Non-determinism warnings are routed into the run log. | Strict mode would crash on ops with no deterministic CUDA kernel. `warn_only` keeps runs going and still *records* any non-determinism. | Bitwise GPU reproducibility is not guaranteed; this is logged and listed under limitations. |
| D-011 | 2026-09-27 | 2 | Decision | The raw hostname is never stored. `machine_id` = first 16 hex characters of SHA-256(hostname). | §5 permits an anonymised identifier; this avoids exposing personal or corporate machine names. | None. |
| D-012 | 2026-09-27 | 2 | Open issue → Phase 9 | With the default augmentation (random crop with 4-px padding, horizontal flip), a bottom-right trigger can be shifted or mirrored to the bottom-left during training | This is a realistic threat model: the attacker poisons stored data and augmentation happens afterwards. | D-013 | 2026-09-27 | 2 | Decision | `training.num_workers: 0` by default | Worker processes on Windows use spawn, which adds start-up cost and complicates RNG control. | May slow data loading. To be reconsidered in Phase 3/4 if it limits GPU throughput. |
| D-014 | 2026-09-27 | design | **Deviation (researcher-approved)** | **Covert attack.** Attack parameters (`attack_type`, `poison_rate`, source/target class, trigger) and attack-revealing identifiers (e.g. `CIFAR10-LF-05-S003`) appear ONLY in ground truth and in the research-harness run index. Investigator-visible dataset IDs are neutral and content-derived (`CIFAR10-TRAIN-<first 12 hex of content hash>`). MLflow (B/C) logs dataset ID, digest, profile and parent, but **not** `attack_type`/`poison_rate`. | §15 and §8, read literally, would hand pipelines B/C the root cause, which contradicts §12 (the pipeline receives only the poisoned dataset) and §46 (no evidence that directly contains the answer). | Deviation from §8/§15. Protects the validity of RQ3. Human-readable **experiment** IDs (`EXP-LF-C-05-S003`) remain harness-level names for folders and the result index. The reconstruction engine must not parse them (enforced by a test). |
| D-015 | 2026-09-27 | design | **Decision (researcher-approved)** | **Threat model: data-store tampering.** The pipeline registers the clean training dataset. An adversary then modifies the stored training data *outside* the instrumented pipeline. The legitimate training job later loads the tampered data. | This is consistent with §12. Evidence can reveal the change without being told (hash mismatch, class-distribution shift, per-sample manifest differences) and without artificial answer-logging. | The time of poisoning is directly observable in no pipeline. At best it can be bounded to the interval between registration and training. The timeline metric accepts bounded times (see `docs/reconstruction.md`). |
| D-016 | 2026-09-27 | design | Decision | Pipeline C runs integrity checks in **record-only** mode. A failed check creates evidence but does **not** stop training. | If C blocked training, the attack would never reach the model in C, so the ML outcome would differ across pipelines and the single independent variable (evidence instrumentation) would be broken. | C models forensic *readiness*, not prevention. Blocking/enforcement is out of scope and listed as a limitation and future work. |
| D-017 | 2026-09-27 | design | Decision | The reconstruction engine may use **only** the evidence store of the pipeline being investigated plus the incident ticket. It may **not** use external reference data such as a fresh CIFAR-10 download. | This models proprietary training data, which cannot be re-obtained from a public source. Allowing the public copy would give every pipeline a clean reference that real investigations usually lack. | Listed as a scope assumption. A sensitivity analysis with a public reference could be future work. |
| D-018 | 2026-09-27 | design | Decision | Every investigation starts from an **incident ticket**: what an affected user or operator could report (timestamp, request ID, the input submitted, observed prediction, expected label). The ticket comes from the *observable* inference output and is identical across A/B/C. It contains no poisoned sample IDs or attack parameters. | Gives every pipeline the same fair starting point. | Equal entry point for all pipelines (§45). |
| D-019 | 2026-09-27 | design | Decision | Forensic loggers **preserve** evidence (manifests, hashes, check results); they do not **interpret** it. For example, C stores the registration-time and training-time per-sample manifests. Which samples changed is computed by the reconstruction engine, not written by the logger. | §46. | The identification of the poisoning source is a reconstruction result, not a logged fact. |
| D-021 | 2026-09-27 | design | Decision (follows D-014) | Investigator-visible artefacts (application logs in evidence stores, MLflow tags, forensic event headers, evidence directory names, incident tickets) identify the run with the opaque **`experiment_uuid`**, never the human-readable experiment ID. In the forensic header (§16), the `experiment_id` field holds the UUID-based run reference `RUN-<uuid>`. The harness keeps `results/raw/run_index.csv` (human ID ↔ UUID ↔ evidence path) outside every evidence store. `reconstruct_incident.py --experiment EXP-…` looks up the index and passes only the evidence directory to `reconstruct()`. | `EXP-LF-C-05-S003` encodes attack type and rate, so it must not appear in evidence (D-014). | Small deviation from the §16 field semantics; the field name is kept. A test will check that no attack-revealing string appears anywhere in an evidence store. |
| D-022 | 2026-09-27 | 3 | Decision (supersedes D-013) | Batches are built **on the device** from uint8 images held in GPU memory. Crop, flip and normalisation run per batch on the GPU. All randomness (shuffle order, crop offsets, flip decisions) comes from a seeded **CPU** `torch.Generator`. `num_workers` is unused. | Avoids Windows DataLoader worker spawn and its RNG complications. The augmentation sequence is independent of device and of global RNG state (a test checks CPU == GPU batches). | Augmentation is equivalent to torchvision `RandomCrop(32, padding=4)` + `RandomHorizontalFlip()`, implemented directly and verified by tests. |
| D-023 | 2026-09-27 | 3 | Decision | Pipeline **data stores**: `data/clean/cifar10_{train,test}.npz`, built only from their official split files. The official download stays read-only, with SHA-256 recorded in `data/manifests/cifar10_raw_integrity.json` and verified on later preparation runs. | Separates the untouched source from the pipeline-owned store that the adversary later tampers with. | Leakage guard: tests confirm that the train store equals `data_batch_1..5` and the test store equals `test_batch`. |
| D-024 | 2026-09-27 | 4 | Decision | The clean test set is evaluated after each epoch **for monitoring only**, to draw the training curve. There is no validation split, no early stopping and no model selection, and the **final-epoch model** is always kept. | Spec §10 asks for per-epoch metrics. Because nothing is selected on the test set, no test information reaches training. | Test accuracy is an unbiased estimate of the final model's clean accuracy. The per-epoch evaluation time is recorded separately (`monitoring_eval_seconds`) so it can be excluded from overhead comparisons. |
| D-025 | 2026-09-27 | 4 | Decision | ResNet-18 = torchvision `resnet18(weights=None)` with a **CIFAR stem**: conv1 7×7/2 → 3×3/1, max-pool removed, fc → 10 outputs. 11,173,962 parameters. | The standard adaptation for 32×32 inputs (spec §11). | Documented in `mlfref/models/resnet.py` and recorded per run in `model_metadata.json`. |
| D-026 | 2026-09-27 | 4 | **Finding → decision** | Models are serialised with `torch.save` into an in-memory buffer, and those bytes are written to disk. | `torch.save(obj, path)` embeds the target **file name** in the zip archive, so identical weights saved under different names get different SHA-256 hashes. Copying or renaming a model at deployment would then make it look like a different model. Found by `test_model_hashing`. | The model SHA-256 now depends on the weights only, and a regression test covers this. |
| D-027 | 2026-09-27 | 4 | **Decision (researcher-approved)** | **30 epochs, AMP fp16** (autocast + GradScaler) for every run. | Calibration (`results/pilot/calibration_training_speed.json`): fp32 100 ms/step (~39 s/epoch), AMP 67 ms/step (~26 s/epoch) on the RTX 1000 Ada Laptop GPU. | Applied identically to A/B/C. Absolute runtimes for RQ4 refer to AMP training. |
| D-028 | 2026-09-27 | 8 | **Decision (researcher-approved)** | Label-flip `poison_rate` is a fraction of the **whole training set**: n = round(rate × 50,000), all drawn from the source class. 5 % = 2,500 of 5,000 automobiles relabelled as truck. | Same denominator as the backdoor rate, so rates are comparable across attacks, and the effect is strong enough for incidents to occur reliably. | The label-flip rate grid is capped at 10 % (the whole source class). 10 % would relabel *every* automobile, so the final grid should stay at or below about 8 % (e.g. 1/3/5 %). | D-030 | 2026-09-27 | 8 | Note | Attack sample selection uses `numpy.random.default_rng(seed).choice`. | D-031 | 2026-09-28 | 10 | Deviation (follows D-014) | MLflow does **not** log `attack_type`, `poison_rate` or **ASR**. CA is logged, as any pipeline evaluates clean accuracy. ASR and other attack metrics go only to harness result files. | Measuring ASR requires knowing the trigger, which a legitimate pipeline cannot know. | D-032 | 2026-09-28 | 10 | **Finding** | Pipeline B records datasets with MLflow's **native** `mlflow.data.from_numpy` digest. By inspection of `mlflow/data/digest_utils.py` (MLflow 3.16.1), that digest is MD5 truncated to 8 hex characters (32 bits), computed over the **first 10,000 flattened values** of the features (≈ 3.3 CIFAR images) and of the targets (first 10,000 labels), plus array shapes. | B should reflect real MLflow practice, not a forensic hash. | MLflow's digest is **not an integrity mechanism**: pixel tampering beyond the first ~3 images, or label changes beyond sample 10,000, leave it unchanged (demonstrated in `test_mlflow_native_digest_behaviour`). This is relevant to RQ1/RQ3 and will be reported. For poisoning spread uniformly over 50k samples, the first 10,000 labels will very likely contain some poisoned samples, so the digest will usually change. It does so by chance, not by design. |
| D-033 | 2026-09-28 | 10 | Decision | Pipeline B logs a per-class **label-distribution profile** (`data_profiles/*.json` artefact) with each dataset input (registration, training, evaluation). | Routine data profiling in legitimate MLflow use. It is not forensic-specific and not attack-specific. Already listed in `docs/evidence_schema.md` §3. | B may detect *that* the class balance shifted, but not *which* samples changed. **Researcher may veto** if this is judged beyond typical practice. |

The model format is incidental to provenance. | None on the comparison. The model artefact in MLflow is a pickled full model; the pipeline's own model file (state_dict, D-026) is unaffected. |
